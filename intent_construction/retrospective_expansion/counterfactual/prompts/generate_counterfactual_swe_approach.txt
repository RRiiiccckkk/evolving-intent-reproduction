You are given a GitHub issue (problem statement) decomposed into a goal and conditions. Your task is to generate a PERTURBED version of a target APPROACH condition.

An "approach" condition is a fix strategy explicitly suggested by the issue author (e.g., "Adding tzinfo arguments should fix this", "Add a hook get_inlines(request, obj=None)", "Return NotImplemented from rich comparison methods").

"Perturbed" means generating an ALTERNATE approach the user *could plausibly have proposed instead*. The user later corrects back to the original. The perturbed version must be:

1. PLAUSIBLE: a real alternative way to fix this same bug
2. CONTRADICTORY: following it would produce a meaningfully different patch
3. SELF-CONTAINED: understandable without other conditions
4. SAME PROBLEM: still addresses the same root issue (don't change the problem)
5. SIMILAR LEVEL OF DETAIL: don't go from "add X" to "rewrite the entire module"

Common perturbation moves for approach:
- Implementation pivot: "add tzinfo arg" → "use a different timezone-aware constructor"
- API design swap: "add a hook get_inlines()" → "add a class attribute inlines_per_request"
- Algorithmic alternative: "return NotImplemented from __eq__" → "override __eq__ to use isinstance check"
- Layer swap: "fix in base class" → "fix in subclass overrides"
- Mechanism swap: "use signal" → "use middleware"

AVOID:
- Approaches that don't actually fix the bug
- Approaches at a completely different level of abstraction (vague vs concrete)
- Approaches that would also require fixing the symptom condition itself

Output JSON format:
{
  "counterfactual_argument": "The full perturbed approach sentence",
  "counterfactual_type": "implementation_pivot | api_design_swap | algorithmic_alt | layer_swap | mechanism_swap",
  "what_changed": "Brief description of what specifically differs",
  "reasoning": "Why this is plausible in context and how it would lead to a different fix"
}
