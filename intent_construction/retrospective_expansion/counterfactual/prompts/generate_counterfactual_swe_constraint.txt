You are given a GitHub issue (problem statement) decomposed into a goal and conditions. Your task is to generate a PERTURBED version of a target CONSTRAINT condition.

A "constraint" condition expresses a requirement, environment limitation, compatibility need, or expected behavior the fix must satisfy (e.g., "must work on Postgres", "should not break backward compatibility", "must raise ValueError", "psql expects options before dbname").

"Perturbed" means generating an ALTERNATE constraint that the user *could plausibly have stated instead* — same form, different specific requirement. The user later corrects this back to the original. The perturbed version must be:

1. PLAUSIBLE: a constraint a real user might state in this issue's context
2. SPECIFIC: not vaguer than the original
3. CONTRADICTORY-OR-DIFFERENT: it should DIFFER from the original such that following it produces a different fix
4. SELF-CONTAINED: understandable without other conditions
5. STAY ON-TOPIC: same module / same general area as the original
6. **PRESERVE GOAL DIRECTION**: do NOT reverse the user's overall intent. If the user wants behavior X enabled, the perturbed constraint must also assume X is wanted — only the *parameters* of how X is constrained should change. NEVER turn a "should support" into a "should NOT support" or vice versa. The user is reporting the same bug; only the requirement details differ.

Common perturbation moves for constraints:
- Value swap: "Postgres" → "MySQL", "SQLite < 3.9.0" → "SQLite < 3.12.0"
- Tighten/loosen: "Python 3.6+" → "Python 3.10+"
- Swap exception type: "must raise ValueError" → "must raise TypeError" (different class, but still raising)
- Add a side-requirement: "must preserve backward compat" → "must preserve backward compat AND not affect query performance"
- Swap target version: "introduced in 4.1" → "introduced in 3.2"

AVOID:
- Reversing the user's goal direction (e.g., "X should work" → "X should not work")
- Trivial paraphrases (no semantic change)
- Changes so drastic the constraint no longer makes sense in this issue
- Constraints that contradict the symptom or trigger of the bug
- Replacing a positive requirement with its negation

Output JSON format:
{
  "counterfactual_argument": "The full perturbed constraint sentence",
  "counterfactual_type": "value_swap | tighten | loosen | exception_type_swap | swap_target | add_side_req",
  "what_changed": "Brief description of what specifically differs",
  "reasoning": "Why this is plausible in context and how it would lead to a different fix"
}
