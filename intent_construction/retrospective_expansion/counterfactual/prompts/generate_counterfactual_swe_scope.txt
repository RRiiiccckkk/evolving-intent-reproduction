You are given a GitHub issue (problem statement) decomposed into a goal and conditions. Your task is to generate a PERTURBED version of a target SCOPE condition.

A "scope" condition defines what the fix should *also* cover beyond the immediate bug, or what other related entity should be considered (e.g., "Card.fromstring likely needs the same treatment", "could also be applied to Min and Max aggregate classes", "expand to other dtypes too").

"Perturbed" means generating an ALTERNATE scope that the user *could plausibly have stated instead*. The user later corrects this back to the original. The perturbed version must be:

1. PLAUSIBLE: a related entity / module / case that would naturally be in scope
2. CONTRADICTORY-OR-DIFFERENT: pursuing it would produce a different fix (different files touched, different code changed)
3. SELF-CONTAINED: understandable without other conditions
4. STAY ON-TOPIC: same module / same general area
5. SAME GRAIN: if the original adds 1 sibling, the perturbed adds 1 sibling (don't replace 1 with 5)

Common perturbation moves for scope:
- Sibling swap: "Card.fromstring" → "Header.fromfile" (different sibling, similar role)
- Family swap: "Min and Max aggregate classes" → "Avg and Count aggregate classes"
- Direction flip: expand → reduce ("apply to N classes" ↔ "apply only to one specific class")
- Generalize/narrow within reason: "categorical dtypes" → "numeric dtypes"

AVOID:
- Replacing with something completely unrelated to the issue area
- Replacing scope with something that's actually goal-level (the bug itself)
- Trivial paraphrases

Output JSON format:
{
  "counterfactual_argument": "The full perturbed scope sentence",
  "counterfactual_type": "sibling_swap | family_swap | direction_flip | generalize | narrow",
  "what_changed": "Brief description of what specifically differs",
  "reasoning": "Why this is plausible in context and how it would lead to a different fix"
}
