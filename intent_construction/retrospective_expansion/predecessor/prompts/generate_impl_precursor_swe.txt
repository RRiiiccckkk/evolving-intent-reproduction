You are simulating a developer who is about to fix a real bug in an open-source repository, but BEFORE the bug fix they were planning a related new feature implementation. They asked you to PLAN the implementation (analyze the codebase and outline the approach, NOT write actual code).

Your job: generate ONE implementation-planning request for a feature that is **adjacent / orthogonal** to the bug, NOT directly inspecting the buggy code path.

The implementation request MUST:

1. Be **planning, not coding**. Phrased as "Can you analyze the codebase and outline how you'd implement X?" — read-only exploration only, no actual code edits.

2. Be **non-trivial and substantive**. Since it's only a plan, the feature itself can be moderately complex (touching multiple files, integrating with existing systems). Avoid trivial one-liner additions.

3. **CRITICAL — be ADJACENT, not OVERLAPPING with the buggy code**:
   - The feature must live in a **sibling module / sibling subsystem / related-but-different subpackage** of the repo. Not the file/class/function where the bug lives. Examples of adjacency:
     * Bug is in `django/db/models/fields/related.py` (FK collation) → impl plan touches `django/db/models/manager.py` or `django/db/migrations/operations/`, NOT the same fields/related code.
     * Bug is in `astropy/io/fits/header.py` (Header.fromstring) → impl plan touches `astropy/io/fits/diff.py` or `astropy/io/registry.py`, NOT header.py.
     * Bug is in `xarray/core/computation.py` (xr.where scalar bug) → impl plan touches `xarray/core/dataset.py` or `xarray/plot/`, NOT computation.py.
   - The plan should be **plausibly possible without ever reading the buggy file**. The agent could in principle complete the plan without inspecting the buggy function.
   - The two share **conceptual/topical context** (same repo subsystem, similar developer audience, related domain) so the conversation feels natural, but they exercise **different code paths**.
   - **Avoid plans whose natural exploration path traverses the buggy class's `__repr__` / `__str__` / `__deepcopy__` / `info()` / `summary()` / `format()` / `to_string()` methods.** When the bug is in a low-level formatting / parsing / repr / dunder method, do NOT propose a high-level "summary", "info", "describe", or "convenience-info" helper that would naturally call into those methods. Pick a feature that touches a different *behavioral* axis (e.g. iteration, configuration, registration, side-effects, lifecycle, validation, plumbing) instead.

4. **NO direct dependency on the buggy API**:
   - Do NOT say "must wrap / call / mirror / depend on" the buggy function.
   - The feature can use *unrelated* APIs from the same repo, public adjacent classes, or different functionality entirely.
   - Bug discovery should happen **only after the user explicitly pivots in turn 3**, NOT as a side effect of analyzing the impl plan.

5. **Plausibility**: a real developer might propose this feature first and only later remember the unrelated bug they wanted fixed.

6. **Distinctness from bug fix**: implementation does NOT solve the bug; the bug is in a separate part of the codebase.

7. Provide 2-4 implementation conditions/specs as design constraints. Use SOFT verbs ("could", "should ideally", "preferably") rather than imperative "must" — this is a plan, not a contract.

8. **Transition phrase** must read as the developer remembering an UNRELATED bug, not "as I analyzed this I noticed":
   - Good: "Hmm, before I dive into the design, I just remembered there's an outstanding issue in [different module] I should fix first — let me deal with that and then come back to this plan."
   - Bad: "While analyzing X, I noticed X has a bug" (this implies the impl analysis exposed the bug — we want orthogonality).

The implementation must NOT:
- Be a simple rephrasing or generalization of the bug fix.
- Suggest fixing the bug as part of the implementation.
- Mention the specific symptom / error / variable names from the eventual bug fix.
- Live in the same file or class as the bug.
